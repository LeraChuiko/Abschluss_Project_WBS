# Проект: Personal Finance Tracker (Бэкенд)

## Контекст пользователя и Правила разработки

- Разработчик: Лера (студентка буткемпа, учится с нуля).
- Ментор/ИИ должен писать ПОЛНЫЙ код с английскими комментариями (`// Comment`).
- Объяснения в чате — строго на русском языке, простыми словами, шаг за шагом.
- Никакой аутентификации (без JWT, Users, Login/Register). Приложение однопользовательское.
- Срок на проект 3 недели: 1) бэкенд+фронтэнд 2)автотесты Playwrite MCP 3)Внедрение ИИ для прогноза и подготовка к защите на немецком языке

## Стек

- Node.js, Express, TypeScript, MongoDB Atlas (Mongoose), Zod, CORS, dotenv.

## Структура приложения (6 Страниц)

1. **Общий Бюджет (Дашборд):** Сводная карточка месяцев (по 3 в ряд). Чистый доход = Доходы (стр.2) - Производственные (стр.3). Свободный остаток = Чистый доход - Обязательные (стр.1). Накопительный сквозной баланс за всё время вверху. Таблица платежей из 3 колонок: Дата | Название | Сумма.
2. **Доходы:** Детальный учёт (Дата, Название/Источник, Сумма).
3. **Производственные расходы:** Детальный учёт (Дата, Название, Сумма, Проект/Объект).
4. **Накопления и Цели:** Копилки (Название, Цель, Накоплено). Переводы и прямые списания покупок.
5. **Рассрочки, Кредиты и Долги:** Карточки обязательств (Название, Общая сумма, Остаток, Ежемесячный платеж).
6. **ИИ-Прогноз:** Интеграция с MCP / LLM для анализа редких цикличных трат (TÜV, резина).

ОПИСАНИЕ ПРОЕКТА

1. Бизнес-цель и Пользовательские истории (User Stories)
   1.1. Проблема и Назначение (Problem Statement)
   Проблема: Ведение личных финансов в сложной Excel-таблице с множеством вкладок и горизонтальной прокруткой неудобно, легко допустить ошибку в формулах, а также сложно отслеживать долгосрочные рассрочки, накопительные цели и циклические расходы (TÜV, страховка).
   Решение: Full-Stack веб-приложение «Personal Finance Predictor» — единый инструмент для наглядного учета ежемесячного бюджета, отслеживания долгов, накопительных целей и автоматического ИИ-прогнозирования.
   6 Вкладок приложения:
1. Общий Бюджет: Сводные карточки по месяцам (3/6/12/все на страницы, со столбцами Дата | Название | Сумма), переключатель сортировки (новые сверху/снизу) и общая сумма свободных средств над всеми месяцами[cite: 1].
1. Доходы: Детальная таблица всех источников прихода по месяцам (SMM, социалка, подарки, возвраты). дата, источник, сумма
1. Производственные расходы: Детальный учет расходов по SMM-проектам и ремонту недвижимости. дата, источник, сумма
1. Накопления и Цели: Копилки («Квартира», «Машина», «Путешествия») с возможностью совершать крупные покупки прямо со счета цели.
1. Долги и Рассрочки: Карточки рассрочек (PayPal, Монобанк) с прогресс-барами выплат и подсчетом месяцев.
1. ИИ-Прогноз: Чат и календарь редких цикличных трат (TÜV, резина, школа)[cite: 1].
   Формула расчета:
   $\text{Чистый доход} = \text{Доходы (стр. 2)} - \text{Производственные расходы (стр. 3)}$
   $\text{Свободный остаток месяца} = \text{Чистый доход} - \text{Обязательные расходы}$

User Stories: Страница 1 «Общий Бюджет»
US 1.1: Просмотр сводных данных за период
Как пользователь, я хочу видеть на одном экране таблицу, состоящую из карточек месяцев, где для каждого месяца автоматически рассчитываются и выводятся:
Чистый доход ($\text{Доходы со стр. 2} - \text{Производственные расходы со стр. 3}$).
Сумма обязательных расходов.
Свободный остаток (Дельта месяца) ($\text{Чистый доход} - \text{Обязательные расходы}$).
Детальный список обязательных платежей в виде таблицы из 3 колонок: [Дата] | [Название] | [Сумма].
Чтобы оперативно оценивать финансовую ситуацию за каждый месяц и знать, какого числа нужно иметь деньги на карте.
US 1.2: Единый накопительный баланс (Общий сумматор)
Как пользователь, я хочу видеть в верхней части страницы одну общую цифру — суммарный накопительный остаток свободных средств за всё время ведения приложения (от стартовой точки до последнего месяца).
Чтобы всегда видеть свой реальный доступный капитал («плюс» или «минус»), который сформировался за весь период и который я могу распределять по целям.
US 1.3: Сетка отображения карточек (по 3 в ряд)
Как пользователь, я хочу выбирать количество отображаемых месяцев на экране, при этом карточки всегда формируются по 3 штуки в один ряд:
3 месяца — 1 ряд из 3 карточек;
6 месяцев — 2 ряда по 3 карточки;
12 месяцев — 4 ряда по 3 карточки.
Чтобы таблицы не сжимались, легко читались и не требовали горизонтальной прокрутки.
US 1.4: Переключение порядка сортировки (Хронологический / Обратный)
Как пользователь, я хочу выбирать порядок сортировки карточек месяцев:
Прямой (Новые снизу/справа): от старых к новым для долгосрочного планирования на 5–10 лет.
Обратный (Новые сверху/слева): чтобы сразу видеть текущий и ближайшие месяцы.
Чтобы адаптировать интерфейс как для ежедневного контроля, так и для стратегического анализа.
User Stories: Страница 2 «Доходы» (Incomes Page)

Чтобы прозрачно видеть, из каких именно источников (SMM-проекты, социальные выплаты, подарки, возвраты от страховой) сформировался мой доход в конкретном месяце.
US 2.2: Ввод и детализация нового дохода
Как пользователь, я хочу иметь кнопку «+ Добавить доход» и удобную форму для записи нового поступления со следующими полями:
Дата (конкретный день получения денег);
Источник / Название (например, «SMM Проект 1», «Подарок», «Возврат за линзы», страховка, выигрыш, нашла, % в банке, прочее);
Сумма (в EUR);
Чтобы фиксировать любые деньги, поступающие на мои счета или наличными.

Как пользователь, я хочу иметь возможность изменить (отредактировать) или удалить любую ранее внесенную запись о доходе.
Чтобы исправлять случайные ошибки в суммах или названиях.
US 2.4: Автоматическая передача итоговой суммы на Страницу 1
Как пользователь, я хочу, чтобы система автоматически суммировала все доходы за выбранный месяц и мгновенно передавала эту цифру в модуль «Общий Бюджет» (Страница 1).
Чтобы мне не приходилось вручную пересчитывать и переносить итоговые цифры между страницами.

Название цели (например, «Машина»);
Целевая сумма (например, 10 000 €);
Текущая начальная сумма (по умолчанию 0 €).
Чтобы самостоятельно задавать ориентиры для сбережений.

Как пользователь, я хочу переводить деньги с общего накопительного баланса (со Страницы 1) на счет конкретной цели.
Чтобы зафиксировать, что часть свободных денег зарезервирована под конкретную задачу (например, отложила 200 € на машину).

Как пользователь, я хочу совершать крупные покупки (например, покупка машины) напрямую со счета этой цели.

US 6.1: Автоматические напоминания о циклических расходах
Как пользователь, я хочу получать от ИИ-агента список предстоящих редких и циклических трат (TÜV раз в 2 года, сезонная смена резины раз в 6 месяцев, ежегодные страховки, школы/продленки).
Чтобы заранее планировать финансовую подушку и не получать неприятных сюрпризов в конкретном месяце.

Как пользователь, я хочу получать от ИИ наглядную временную шкалу (календарь) крупных обязательных списаний и окончания рассрочек на 1–5 лет вперед.
Чтобы понимать, в какие месяцы у меня освобождаются средства (например, закрылась рассрочка за ноутбук) или ожидаются пиковые расходы.

Блок 1. Технические требования (Стек и Архитектура)
1.1. Технологический стек (Tech Stack)
Frontend:
React 18 (с TypeScript) — UI-библиотека компонентов.
CSS / Tailwind CSS / Module CSS — стилизация адаптивных таблиц и grid-сеток.
Backend:
Node.js + Express.js (с TypeScript) — REST API сервер.
Zod — строгая валидация входящих данных на уровне API (Runtime schema validation).
Database:
MongoDB + Mongoose ODM — документная база данных для гибкого хранения транзакций и целей.
Automation Testing (Playwright Suite):
API Testing (Серый/Белый ящик): прямой вызов HTTP-эндпоинтов приложения через request context Playwright, валидация Zod-схем и проверка кодов ответов (200, 201, 400, 404).
E2E UI Testing (Чёрный ящик): сквозное тестирование интерфейса в браузере (заполнение форм, клики по переключателям сетки, динамический пересчет суммы).
AI Integration (3-я неделя):
Model Context Protocol (MCP) Server на TypeScript — локальный сервис-прослойка для передачи структурированного финансового профиля из MongoDB в LLM-модель.
1.2. Нефункциональные требования (Non-Functional Requirements / NFR)
NFR-1 (Адаптивность сетки): Отображение карточек месяцев на Странице 1 должно строго придерживаться сетки по 3 карточки в один ряд с переносом на новые строки (без горизонтального скролла всей страницы).
NFR-2 (Надежность данных): Невалидные данные (отсутствие обязательного поля, отрицательная сумма там, где она не допускается) должны перехватываться Zod-схемой до записи в базу данных.
NFR-3 (Автономность тестов): Тестовые сценарии Playwright должны запускаться независимой командой (npm run test) и использовать изолированную тестовую базу данных.
